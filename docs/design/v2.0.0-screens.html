grubForge v2.0.0 · design proposal · 2 October 2026

grubForge 2.0, screen by screen

Every screen of the new grubForge, drawn before any code is written. It covers what you see, the order you move through it, which settings are picked from a list instead of typed, and the keys and buttons. The answers you give at the end decide what gets built.

Your brief: "high quality UI and easy to use structure … caring for formatting, use of colors, contrasts, and following flow of use from selecting, tabbing, buttons … leave as little to the user to write where options are known … and besides the help shortcuts, a manual on how to use it."

Decided · Javier, 2 October

  1. Settings layout: a form, with every control visible.
  2. Save and Rebuild are two buttons. Save writes your changes and keeps them. Rebuild puts them into the boot menu. grubForge always shows when something is saved but not rebuilt yet. See Save & rebuild.
  3. Plain names, with the GRUB name in the help line.
  4. Entries made by other tools stay fixed where their tool puts them (#20).
  5. Support every major distribution, not only Fedora and openSUSE. See Distributions.
  6. A closing note in the terminal, and a warning on quit when saved changes aren't rebuilt yet.

"So far, it is looking very good!"

What the research says

Sources: well-regarded terminal tools (htop's setup screen, lazygit, k9s, gitui, nmtui, archinstall, Posting), the two GUI tools for this exact job (Grub Customizer, KDE's GRUB settings), WCAG and clig.dev. These seven points decide everything below.

Pick, don't type

A setting with known values is a list or a switch. Typing is only for names and unusual kernel options. Grub Customizer and KDE both work this way.

phoenixnap.com/kb/grub-customizer · lxr.kde.org kcm-grub2

Nothing to memorise

A hint bar at the bottom always shows the keys that work right now, and F1 explains the setting you're on. gitui calls this "context based help."

github.com/extrawurst/gitui · man htop

Words as well as colours

A changed setting says "changed", a warning says "!" and a sentence. Colour is never the only signal, and on the 8-colour text console it may be all you get.

WCAG 1.4.1 · github.blog accessible CLI

Draft, review, apply

Edits are a draft until you apply them. Before anything is written, a review lists every change as old → new. The password is asked once, at apply.

kcm-grub2 save flow · clig.dev

Confirm by risk

A small change gets one review. Restoring a backup or removing an entry gets a confirmation where "No" is the default.

clig.dev · k9s

Same keys everywhere

Tab next, Enter open/confirm, Space toggle, Esc back. Every F-key has a letter alternative, because consoles can swallow F-keys.

nmtui · YaST · Textual defaults

A real manual

Help says what this key or setting does. The manual says how to do a task, with examples first, and a contents list you can jump around in.

clig.dev · Textual MarkdownViewer

The frame around every screen

The top two rows are forgekit's locked layout, the same as alacrittyForge and bitlaForge: a title row and a menu bar with underlined letters. New at the bottom: a changes bar that appears when something isn't saved yet, or saved but not rebuilt yet, and a hint bar that changes with what is selected.

Decision 1 · form or table?

Form (recommended): every control is visible, so you can see a setting is a switch or a list before touching it. That's what htop's setup, Grub Customizer and the KDE settings do, and it suits people who aren't engineers.

Table (alacrittyForge today): rows of Key · Value · Staged, with a list opening at the cell on Enter. It's tidier for 40 settings, but the kind of control is hidden until you press a key.

If you choose the form, I'd later bring alacrittyForge's settings onto the same pieces, so the Forge Suite stays consistent.

The kinds: another Linux kernel, another operating system on a disk, memory test, firmware settings, or an empty entry you write yourself. Kernels, images and disks are read from the computer, so the old placeholder "YOUR-UUID-HERE" is gone. "Edit by hand" opens the text for experts, checked before it's added.

Decision 4 · entries made by other tools (#20)

Today, saving your own order copies the snapshot entries into it while the snapshot tool keeps adding them too, so they show up twice. Recommended: those entries stay with their tool. They are shown as "fixed · its tool places it" and can't be moved, so the duplicate can't happen.

Save & rebuild

Settings, boot order and themes all go into the same draft, and the changes bar counts them. Save (F10) shows one review of everything, then backs up and writes. Rebuild (F9) runs grub-mkconfig, so the boot menu picks the saved changes up. Two buttons, each doing one thing you can see. The review offers both together, for when you know you want both.

Distributions

GRUB is the same program everywhere, but distributions keep its files in different places and call its tools by different names. grubForge 2.0 finds these by itself and says what it found on the Overview. Each row gets tested in a VM before release, and anything not proven there is marked so in the README.

The Fedora row is the big one: those systems don't put entries in grub.cfg at all. That's why grubForge can't be working there today (#24). How it should look on the Boot menu screen there is a small design of its own, which I'll show you before building it.

Help and the manual

Help (quick)

  • The hint bar always shows the keys for what is selected.
  • F1 explains the setting or button you're on, and links to its manual page.
  • ? lists every key on one page.
  • Help ▾ menu: Manual, Keys, License, About.

The manual (how to do things)

  • It opens in the app (Help ▾ Manual, or M), with a contents list on the left.
  • Each page leads with the steps for a task, then the details.
  • The same pages are on GitHub and installed with the package, so they can be read without the app.

On a plain text console (#21)

When the desktop is broken, a text console (Ctrl+Alt+F3) is where you'll run grubForge. That's exactly when it matters most. The console has 8 colours and no emoji, so every colour comes from forgekit's roles, every symbol from its table with a plain fallback, and the focused control is the only blue one.

How it gets built

Release discipline as always: one logical commit per phase, docs and version, then a tag. You test before anything is released.

  1. forgekit v0.5.0: the pieces above, with a demo and console checks.
  2. The frame, Overview and Settings, on the new forgekit, with Save, Rebuild and the quit warning.
  3. Boot menu, including Add an entry, Find other systems, and the #20 fix.
  4. Themes and Backups.
  5. The manual and the console, plus grubforge --version and --help printing instead of opening the app (#22), and every major distribution's paths and tools (#24).
